### Approach

A camera preset is a pure view transform applied *after* the drive has computed where the car is. It must not touch the route.

That separation is not stylistic, it is required by R1 and by the T7 acceptance. The plan requires route decisions to be deterministic functions of seed alone (line 105: independent deterministic streams for "city generation, route decisions and musical parameters"; line 109: "The reproducibility promise concerns descriptors, route decisions and score events"; R1 at line 56), and T7's test list includes "Reduced speed must lower angular velocity without changing route decisions" (line 428). If a preset fed back into path generation — for example if the overhead camera made the route generator pick wider turns — then `?seed=marlowe` would produce two different drives depending on which camera the viewer happened to be using, and the cross-reload determinism tests in `tests/drive.test.ts` and the e2e seed-identity checks in `tests/e2e/interface.spec.ts` would both become preset-dependent. The design keeps the drive producing a *path pose* (a position on the road plus a forward direction plus a travel-time value), and the preset turns that path pose into a *camera pose* (world position, look-at target, pitch). Nothing flows backwards.

The presets themselves are data, not branches. Four entries in one table, read by one function. Adding a fifth preset later — a wing-mirror view, a passenger seat — is then a data edit, which is what the AGENTS.md this plan follows asks for (plan line 50 points at it; there is no AGENTS.md inside this repository): "Cases, rules, thresholds, mappings... put them in data behind one small piece of logic that reads them". A `switch` on preset name inside the frame loop would be the wrong shape here and would make the reduced-motion variants a second parallel `switch`.

The eased transition is one interpolator over that table. Because every preset is the same shape — a small record of numbers — a single lerp across the record handles all sixteen possible source/target pairs with no per-pair code.

### Each file and exactly what changes in it

**`src/camera-presets.ts` (new, the only new module)**

This is the whole feature's logic, and it is pure: no `three` imports beyond types if even that, no DOM, no clock. That purity is what makes `tests/camera-presets.test.ts` able to cover almost all of the behaviour without a browser.

It exports:

1. `CAMERA_PRESETS` — an ordered array of four records, one per preset the operator named ("Hood, rear-window, low chase, and slow overhead" — the record's words). Each record carries a stable id, a human label, the geometric offsets expressed in the drive's own frame of reference (lateral, vertical, longitudinal relative to the car's position and heading), a pitch, a look-ahead distance along the path for the look-at target, a transition duration, and a `reduced` sub-record holding the overrides for that preset's reduced-motion variant.

   The four, matching the operator's words:
   - `hood` — low, slightly forward of the car's origin, near-zero pitch, long look-ahead down the avenue. This is the "six feet lower" case in the operator's second line ("The same street is a different city from six feet lower").
   - `rear-window` — behind the car's origin, roughly eye height, looking *backwards*: the look-at target is behind along the path, so the city recedes. This is the only preset whose look-at target is at a negative look-ahead; keep that expressible in the same field rather than adding a `facing` boolean.
   - `low-chase` — behind and slightly above, pitched down a little, the conventional third-person follow (the operator's "low chase"; `low-chase` is the URL-safe id, "Low chase" the label).
   - `slow-overhead` — well above, pitched steeply down, with a slow yaw drift so the view is not a static top-down plate. "Slow" is the operator's word and it means this preset carries its own motion, which is exactly why it needs a reduced-motion variant with the drift reduced or removed. How high this goes is the open decision in Questions.

   Each record also needs a `clearanceRadius` — the radius the clearance test must keep outside building volumes for this camera. It differs per preset: the hood camera sits inside the road corridor and needs the same clearance the T7 camera needed; the rear-window camera sweeps a different arc through an intersection; the overhead camera may be above every building and need none. Putting it in the table keeps the clearance check one parameterised assertion instead of four.

2. `reducedVariant(preset)` — returns the preset with its `reduced` overrides merged in. One spread, not four functions. The operator's requirement is "each with its own reduced-motion variant", and merging overrides onto the base record is the form that makes each variant independently tunable while guaranteeing it exists for every preset — a test can assert `CAMERA_PRESETS.every(p => p.reduced)` and that is the whole "each with its own" contract.

3. `nextPreset(currentId)` — returns the id of the next entry, wrapping from the last back to the first. Index arithmetic over the array, resolved by id so the caller never holds an index.

4. `resolvePose(preset, pathPose, reducedMotion, driftTime)` — the pure pose function. Takes the drive's path pose, applies the preset's offsets in the path frame, returns the camera's world position, look-at target and pitch. `driftTime` is active time, used only by `slow-overhead`'s yaw drift; the other three ignore it, which is correct and is not a special case worth branching on — a drift amplitude of zero in the table makes it a no-op.

5. `transitionPose(fromPreset, toPreset, progress, pathPose, reducedMotion, driftTime)` — resolves the pose under both presets against the *same* path pose and eases between them. Easing the *resolved poses*, not the raw preset records, is the correct choice and worth being explicit about: interpolating raw records and then resolving would also work for position, but it makes the look-at target behave strangely when the rear-window preset's negative look-ahead crosses through zero on the way to a positive one, producing a moment where the camera looks at its own origin and the view direction is undefined. Interpolating the resolved look-at *points* passes smoothly through the car instead, which reads as a sweep rather than a glitch.

   The easing curve is a single smoothstep. It must not overshoot. An ease-back or elastic curve would move the camera momentarily *further* than the target preset, which for `hood` means dipping below road level and for `low-chase` at a turn means swinging outside the clearance envelope the preset table promises. A monotone non-overshooting curve is both the simpler choice and the correct one on edge cases.

**`src/app.ts`**

The frame loop and the input wiring. Changes:

- Hold the camera-preset state: `{ currentId, previousId, transitionStartActiveTime }`, or `previousId === null` when settled. Three fields, no state machine class.
- In the per-frame step, after the drive produces its path pose and before the camera transform is written, compute the camera pose. When settled, `resolvePose`. When transitioning, compute `progress = (activeTime - transitionStartActiveTime) / duration`, clamp to 1, call `transitionPose`, and when progress reaches 1 clear `previousId`.

  **The duration must be measured in the drive's active time, not `performance.now()`.** The plan requires pause to freeze movement, atmosphere and score position and requires resume to reset timing anchors so elapsed wall-clock is not replayed (both rules are on line 138; the Pause behaviour example at line 72 makes the same promise). A camera transition is movement. If it reads wall-clock, then pausing mid-transition and resuming ten seconds later finds the transition already expired and the camera snapped — which is the single most visible way to break the "eased transitions" the operator asked for. Using active time makes pause freeze the transition in place for free, with no pause-specific code.

  A consequence the implementer should accept deliberately: the `?test=1` speed multiplier accelerates movement time (plan lines 144 and 297), so it also accelerates preset transitions. That is desirable — it lets the e2e spec step through a transition quickly — and it is consistent with the multiplier affecting "driving only" (line 297's own words), since the camera is part of the drive. It does not touch music or atmosphere (line 144).

- Add the keydown handler for the cycle key. It must follow the same rules the plan already establishes for Space (lines 198 and 506):
  - ignore the event when `event.repeat` is true, so holding the key does not spin through presets at the keyboard repeat rate;
  - ignore it when the event target is an interactive HUD control, so a focused button or the volume slider keeps its own keyboard behaviour and a button activation does not also cycle the camera;
  - call `preventDefault()` only if the key would otherwise do something in the page.

  The handler sets `previousId = currentId`, `currentId = nextPreset(currentId)`, `transitionStartActiveTime = activeTime`.

  Proposed key: `c`. Space (pause) and Escape (About focus, line 198) are the only keys the plan binds, so `c` collides with nothing. If the implementer finds a collision with a binding T12 introduces, any free single letter works; the key is a one-line data constant in `src/camera-presets.ts` so moving it is trivial.

- Register and unregister the listener alongside the existing listeners, so application teardown (plan lines 190 and 368) removes it. Leaving it attached after teardown would violate the verification contract's resource checks — "Bounded audio voices, scheduled events, timers and listeners" and "Correct cleanup after reset and teardown" (plan lines 290–291) — which the completed e2e suite enforces at T13.

- On new-seed reset (T12), **do not** reset the preset. The plan's reset contract (lines 75, 194 and 504) resets city, route, atmosphere and score to time zero while *preserving* volume, mute and running/paused state. The preset is a view preference in the same class as volume, not world state, so preserving it is the consistent reading, and it is what the viewer will expect when they reroll a seed to find a better city from the camera they chose. This is an assumption, stated here and carried; it is safe because it is strictly reversible by one keypress and because the alternative (resetting to `hood`) is a one-line change if the operator disagrees. Do clear any *in-flight* transition on reset, since active time returns to zero and a transition anchored at an old active time would otherwise compute a negative progress.

**`tests/camera-presets.test.ts` (new, Vitest)**

Covers everything that is pure. This file is not the acceptance command but it runs inside `npm run test` and therefore inside `npm run verify`, so it protects the feature in CI:

- The table has exactly the four presets the operator named, every entry has a unique stable id, and every entry has a `reduced` variant. This is the "each with its own reduced-motion variant" contract as one assertion over data.
- `nextPreset` cycles through all four in order and wraps from the last to the first; calling it four times from any starting id returns to that id.
- `nextPreset` on an unknown id returns the first preset rather than throwing. This matters because `e06bde4c` will put the preset id in a URL hash, where anyone can type anything.
- `resolvePose` is deterministic: same preset, same path pose, same inputs, same output.
- `resolvePose` under the same path pose returns measurably different camera heights for `hood` versus `slow-overhead` — the operator's "six feet lower" claim as a number.
- `rear-window` produces a look-at target behind the car's position along the path direction, while the other three look ahead.
- `transitionPose` at progress 0 equals `resolvePose(from)`, at progress 1 equals `resolvePose(to)`, and is monotone in between on each interpolated component — this is the no-overshoot guarantee, and it is the assertion that fails if someone swaps in an elastic easing curve.
- `transitionPose` with progress clamped outside [0,1] returns the endpoint poses rather than extrapolating.
- Under reduced motion, every preset's transition duration is at least its normal duration, and `slow-overhead`'s drift amplitude is reduced. "No sudden turns" (R4, line 59) means the reduced variants ease more slowly, never faster.
- Clearance: for each preset, drive a deterministic fixture route through a straight segment and both turn directions, and assert the camera position plus its `clearanceRadius` stays outside the building volumes `src/city.ts` reports. This reuses T7's clearance helper rather than reimplementing it; if T7 did not export one, extracting it from `tests/drive.test.ts` is the lazier move than writing a second. Run this over the supported viewport proportions T7 already parameterises (line 428), since the near-plane footprint changes with aspect.
- The route is unchanged by the preset: generate the route under each of the four presets and assert the sequence of route decisions is byte-identical. This is the R1 guard described in Approach.

**`tests/e2e/camera-presets.spec.ts` (new, Playwright — the acceptance)**

Covers what only a browser can show. Runs in both configured projects (Chrome channel and Playwright Firefox — plan line 270) like every other spec:

- Load with `?test=1&seed=<fixture>`, click Start, wait for readiness. Record `cameraPose` and `cameraPreset`.
- Press the cycle key. Sample `cameraPose` across several frames during the transition and assert it moves through intermediate values rather than jumping — specifically, that at least one sample lies strictly between the start and end poses. This is the assertion that proves "eased transitions" rather than "switched"; a hard cut produces only endpoint samples and fails it.
- Assert the settled pose equals the target preset's pose and `cameraPreset` is the target id.
- Press the key four times total and assert the cycle returns to the starting preset, having visited all four ids.
- Hold the key down (dispatch with `repeat: true`) and assert the preset does not advance.
- Focus a HUD control, press the key, and assert the preset does not advance and the control's own behaviour is unaffected.
- Start a transition, pause (Space), wait, and assert `cameraPose` is unchanged across the pause — the active-time anchoring. Resume and assert the transition completes from where it froze rather than snapping.
- Reload with `prefers-reduced-motion: reduce` emulated. Cycle presets and assert the transition takes longer in active time and that the per-frame pose delta stays below the normal-motion maximum. This is the comfort guarantee: the thing that makes someone sick is a fast camera swing, so the test measures the swing rate, not just the duration.
- Toggle reduced motion live mid-transition (T8 supports live preference changes, line 440) and assert no discontinuity: the pose delta between consecutive frames stays bounded across the switch.
- Assert draw calls stay below 150 while `slow-overhead` is active. This is the only preset that widens the view enough to threaten the budget, and the budget is one of the seven required release checks (plan line 276; already asserted for the city view by T5 at line 400). Catching a violation here, in the task that introduces the risk, is cheaper than having T13 catch it.
- Collect console and page errors from before navigation through every scenario, as every other spec in this suite does (plan line 274).

### Edge cases and what happens at each

**Key pressed while a transition is in flight.** Do not queue, do not ignore. Set the transition's `from` to the *current interpolated pose* — capture it as a frozen pose record — and ease from there to the new target over the new preset's duration. Ignoring the key makes the control feel broken when someone taps through presets quickly, which is exactly how people use a cycle key; queueing makes the camera visit presets the viewer has already skipped past. Easing from the live pose means four fast taps produce one smooth sweep ending at the fourth preset. The implementation cost is one extra field holding the frozen pose instead of a `fromPreset` id.

**Reduced-motion preference changes mid-transition.** T8 handles live `prefers-reduced-motion` changes (line 440). Recompute the duration from the active preset's reduced variant and rescale the remaining progress so the pose does not jump. Concretely: the elapsed fraction already travelled stays fixed and only the remaining time stretches. Failing to rescale makes the camera snap at the moment the viewer enables the comfort setting, which is the worst possible moment for a snap.

**Pause mid-transition.** Handled structurally by anchoring on active time — the transition freezes with everything else and resumes from the same progress. No pause-specific code. Verified in the e2e spec.

**Page hidden mid-transition.** The plan pauses on hide ("Hiding a running page pauses it", line 73; implemented by T8 at line 440). Same mechanism, same result.

**New seed mid-transition.** Active time returns to zero, so `transitionStartActiveTime` from the old session would yield negative progress. Clear the transition on reset: settle immediately to the current preset. The preset id itself is preserved (see `src/app.ts` above).

**WebGL context loss mid-transition.** The plan stops the experience and offers reload (line 202). The camera state goes away with the app; no special handling, but confirm the keydown listener is removed with the rest so a key press on the dead page does not throw.

**Resize or fullscreen entry.** Aspect ratio changes the near-plane footprint, which changes clearance (plan lines 71 and 200). The per-preset clearance assertions must run across the supported viewport proportions, and the `clearanceRadius` values in the table must be chosen for the widest supported aspect, not the test default. A preset that clears at 16:9 and clips at 21:9 is a real failure mode here, and `hood` — the lowest and most forward camera — is the one most exposed to it.

**Fog and far-plane distance.** The plan chooses fog and far-plane "from the minimum distance to the loaded boundary as the camera moves within its chunk" (line 115) — the plan's own words already name the *camera*, not the car. That computation must therefore use the camera position. `rear-window` pushes the camera backwards and `slow-overhead` pushes it up and back; under either, the camera is measurably closer to one edge of the loaded 5×5 neighbourhood than the car is. If the fog distance is computed from the car, the overhead and rear views will show the neighbourhood boundary popping in beyond the fog — and an implementation doing that would itself deviate from line 115. Whether a change is needed depends on how T8 wrote it; if T8 already passes the camera position, nothing changes here. If it passes the drive position, this task must switch it, and `src/atmosphere.ts` joins the Files list.

**Preset identity for `e06bde4c`.** The ids must be stable strings (`hood`, `rear-window`, `low-chase`, `slow-overhead`), URL-safe, and never array indices. `e06bde4c` will write one into a URL hash that someone sends to a friend (the record's own second line); if a fifth preset is later inserted in the middle of the array, an index-based id would silently change which camera every shared link opens. Exporting ids as a table-driven constant also gives `e06bde4c` a validation list for free.

**Unknown preset id arriving from outside.** `nextPreset` and the app's initial state both fall back to the first preset rather than throwing. Again driven by `e06bde4c`: a hand-edited or truncated hash must not break the drive.

**`slow-overhead` and the drive's own turning.** The overhead camera looks down, so the car's heading changes rotate the whole view. Under normal motion that is the point. Under reduced motion, a 90° intersection turn seen from directly overhead is a full-screen rotation — the single most nausea-inducing thing this feature can produce. The reduced variant for `slow-overhead` should therefore damp the camera's yaw response to heading changes, not just slow the preset transition: let the camera's yaw lag the car's heading and catch up gently, so the world rotates slowly even when the car turns at the normal rate. This is the "no sudden turns" clause of R4 (line 59) applied to the one preset that amplifies turns rather than attenuating them, and it is why the operator's "each with its own reduced-motion variant" is a real requirement rather than boilerplate.

**Draw calls under `slow-overhead`.** Instanced pools mean the draw-call count is driven by pool count, not visible instance count, so the budget should hold. "Should" is not evidence — the plan is explicit that instancing's effect "must be measured" (line 117). The e2e assertion above measures it.

**Bundle size.** One small pure module and a few lines of wiring. No effect on the 300,000-byte gzipped budget (plan line 266 fixes the interpretation).

### Why the acceptance command fails before and passes after

`npm run test:e2e -- tests/e2e/camera-presets.spec.ts`

Before: the command does not resolve at all. There is no `package.json` in this repository, so npm exits non-zero before any script runs. After T1–T8 are implemented but before this task, `npm run test:e2e` resolves and Playwright runs, but `tests/e2e/camera-presets.spec.ts` does not exist and Playwright exits non-zero on the missing test file. The project's own goal document anticipates and endorses exactly this baseline: "acceptance commands that fail with 'package.json missing' or exit non-zero today are exactly right" (`.factory/goals/2fd2a8ea.md:26`, verified verbatim).

After: the spec exists and passes only if all of the following are true in a real browser — the key cycles through four distinct presets and wraps, the pose moves through intermediate values rather than cutting, key-repeat and focused-control cases are suppressed, a transition freezes across pause and resumes from its frozen progress, the reduced-motion variant both lasts longer and swings more slowly, a live preference change produces no discontinuity, and the draw-call budget survives the widest preset. Each of those is a distinct way the feature can be wrong, and each fails this one command.

The command is targeted rather than `npm run verify` because `verify` runs lint, typecheck, the whole unit suite, a build, the whole e2e suite and the size gate in order (plan line 262) — it would fail for reasons unrelated to this task and would not isolate this work. The `npm run test:e2e -- <spec>` form is the plan's own targeted-acceptance pattern, used by T3 (line 374), T5 (line 402) and T12 (line 510). `npm run test -- tests/camera-presets.test.ts` was the other candidate; it is faster and covers the pure logic, but it cannot prove the two things the operator actually asked for — that the preset is *cycled by key* and that the transition is *eased* on screen. The e2e command proves both and still fails if the pure logic is wrong, because the pure logic drives the poses it samples. The unit file still exists and still runs inside `verify`; it is just not the proof.

## Questions

**Q1 — How high does `slow-overhead` go: above the rooftops, or below them?** This is a product decision about what the drive looks like, not an implementation detail, and it has consequences in both directions.

- *Above the tallest building.* Reads unambiguously as "overhead" and gives the city-as-map view the operator's second line implies. Costs: the camera sees to the edge of the loaded 5×5 neighbourhood (plan line 115), so the fog and far-plane distances chosen under that rule and added by T8 (line 438) become visible as a boundary rather than a haze; the 25-chunk residency may stop being sufficient for a view that reads as a city rather than a patch; and the wide view is the one place the sub-150 draw-call budget (line 276) is at risk. Any of those three could turn into a change in `src/streaming.ts` or `src/atmosphere.ts`, which is scope this task does not currently hold.
- *Below the tallest rooftops, above the street lights.* Keeps every existing budget and boundary untouched and costs nothing beyond the table values. But it is a high chase camera, not an overhead one, and it will not deliver the "different city from six feet lower" contrast the operator is describing.

The table makes this a one-number change either way, so it does not block starting. It does determine whether this task also owns a fog/streaming change, so it should be answered before the e2e draw-call assertion is tuned.

**Q2 — Which module writes the camera transform each frame?** I could not establish this, because the code does not exist.

What I read: plan `035a973a` assigns the `THREE.PerspectiveCamera` object's creation to T3 (`src/scene.ts` is in T3's file list at line 364; the description "Create the renderer, camera, empty scene and resize handling" is at line 366); assigns the route queue and intersection-curve evaluation to T7 (`src/drive.ts` and `tests/drive.test.ts` at line 424, description at line 426); and assigns integration to T8 with a file list of `src/app.ts`, `src/scene.ts`, `src/drive.ts`, `src/atmosphere.ts`, `src/ui.ts`, `src/test-api.ts` (line 436) under the instruction "Connect motion to streaming" (line 438).
